# 1-1. 소개

리전마다 Transit Gateway를 하나씩 두고 peering으로 잇는 방식은 리전이 두세 개일 때는 잘 동작합니다. 하지만 리전이 늘면 이어야 할 peering이 빠르게 늘고, 운영·개발·공유 서비스 같은 환경을 나누려면 리전마다 라우팅 테이블을 만들고 어느 연결(attachment)을 어느 테이블에 붙일지 손으로 맞춰야 합니다. 리전 하나를 더 열 때마다 같은 일을 처음부터 다시 하게 됩니다.

AWS Cloud WAN은 이 일을 **정책 문서 하나**(core network policy)로 바꿉니다. 리전은 **그 리전의 접속 지점**(core network edge) 하나를 더하는 것으로 늘어나고, 환경은 **세그먼트**(segment)라는 격리 구역으로 나눕니다. 어디와 통신할 수 있는지는 이 문서에 적힌 대로 정해지고, 라우팅 테이블을 리전마다 고칠 일이 없습니다.

| 항목 | 내용 |
|---|---|
| 대상 | VPC와 Transit Gateway를 써 본 분 |
| 레벨 | 200 |
| 시간 | 2시간(이론 1시간, 실습 1시간) |
| 준비물 | 웹 브라우저. 참가자마다 AWS 계정 1개를 드립니다 |
| 리전 | 아시아 태평양(서울) `ap-northeast-2`와 미국 서부(오레곤) `us-west-2` 두 곳을 씁니다 |

온프레미스 환경은 AWS 안에 만든 별도 VPC로 흉내 냅니다. 이 문서에서는 이것을 **온프레미스 모사 VPC** 라고 부릅니다. 실제 온프레미스처럼 Site-to-Site VPN으로만 Cloud WAN에 연결하므로, 연결 방식과 경로 동작은 실제 구성과 같습니다.

모르는 용어는 [용어 풀이](glossary.md)를 보세요. 실습을 시작하기 전에 준비할 것은 [1-2. 사전 준비](prerequisites.md)에 있습니다.

## 1-1-a. 왜 Cloud WAN인가요 { #why }

여러 리전과 여러 환경을 쓰는 네트워크를 Transit Gateway로 만들면, 리전마다 Transit Gateway를 하나씩 두고 서로 peering으로 잇습니다. 모든 리전이 서로 통신해야 하면 peering 수는 리전 수 n에 대해 **n(n-1)/2개**입니다. 리전이 2개면 1개지만, 5개면 10개입니다. peering을 만든 뒤에도 각 Transit Gateway의 라우팅 테이블에 상대 리전의 대역을 넣어야 하므로, 손으로 관리할 것은 peering 수보다 더 빨리 늘어납니다.

Cloud WAN은 이것을 **core network** 하나와 그것을 적어 둔 **core network policy** 하나로 바꿉니다. policy는 JSON 문서입니다. 어느 리전에 edge를 둘지, 세그먼트를 무엇으로 나눌지, 어느 세그먼트끼리 통신할지를 **한 파일에** 적습니다. 이 워크숍에서 참가자가 고치는 것은 결국 이 파일 하나입니다.

core network는 그 정책대로 만들어지는, 리전들을 잇는 네트워크 그 자체입니다. 그 네트워크가 리전마다 내놓는 접속 지점이 **core network edge** 입니다. VPC는 이 edge에 붙습니다. edge 수는 리전 수 n에 대해 **n개**이고, **edge끼리 잇는 일은 Cloud WAN이 알아서 합니다.** 참가자가 하는 일은 정책에 리전 이름과 ASN을 한 줄 더 적는 것뿐입니다.

ASN(Autonomous System Number)은 **네트워크마다 붙이는 식별 번호**입니다. 네트워크끼리 경로를 주고받을 때 "이 경로는 어느 네트워크에서 왔는가"를 이 번호로 구분합니다(그 주고받는 약속이 **BGP**(Border Gateway Protocol)이고, [2-3](lab2.md)에서 직접 봅니다). 여기서는 edge마다 다른 번호를 주면 된다고만 알면 됩니다. 실제 값은 [주소 설계](#addressing)의 ASN 표에 있습니다.

| 구분 | Transit Gateway 구성 | Cloud WAN 구성 |
|---|---|---|
| 리전 n개를 모두 잇기 | peering `n(n-1)/2`개 | core network edge `n`개 |
| 리전을 하나 더 열 때 | 기존 리전 수만큼 peering을 더 만들고 양쪽 라우팅 테이블을 고칩니다 | 정책의 `edge-locations`에 한 줄을 더합니다 |
| 환경 나누기 | 리전마다 라우팅 테이블을 따로 만들고, 연결마다 어느 테이블에 붙일지 지정합니다 | 세그먼트를 만들고, 연결에 태그를 붙입니다 |
| 통신 범위를 정하는 곳 | 리전마다 흩어진 라우팅 테이블과, 어느 대역을 어느 테이블에 올릴지 정하는 설정(propagation) | core network policy 문서 하나 |
| 바꾼 내용을 적용하는 방법 | 리전마다 따로 적용합니다 | policy version을 만들고 change set을 검토한 뒤 한 번에 실행합니다 |

표의 마지막 줄에 나오는 두 가지는 이 워크숍에서 계속 쓰므로 미리 적어 둡니다. **policy version** 은 정책 문서의 새 판입니다. 문서를 고치면 새 번호의 판이 하나 생깁니다. **change set** 은 그 새 판이 지금 상태를 무엇으로 바꾸는지 적은 **변경 목록**입니다. 새 판을 만드는 것만으로는 아무것도 바뀌지 않고, 변경 목록을 실행해야 적용됩니다. [2-4](lab3.md)에서 직접 해 봅니다.

세그먼트는 기본적으로 **자기 세그먼트 안에서만** 통신합니다. 운영 환경과 개발 환경을 막으려고 따로 할 일이 없다는 뜻입니다. 반대로 열어 줄 때는 정책의 `segment-actions`에 `share`를 적습니다. 세그먼트는 리전마다 따로 만드는 것이 아니라 core network 전체에서 하나입니다. 이 워크숍에서는 `prod`, `dev`, `shared`, `onprem` 네 세그먼트로 이 동작을 직접 확인합니다.

## 1-1-b. 워크숍의 목표 { #goal }

이 워크숍은 여러 리전과 여러 환경을 가진 네트워크를 맡은 분이, Cloud WAN의 세그먼트와 정책으로 그 네트워크를 관리할 수 있는지 직접 판단할 수 있도록 만들었습니다.

워크숍을 마치면 다음을 할 수 있습니다.

1. core network, core network edge, 세그먼트, 연결(attachment)이 서로 어떤 관계인지 설명합니다.
2. core network policy에서 세그먼트가 서로 격리되는 기본 동작과 `share`를 적었을 때의 효과를 설명합니다.
3. 연결에 태그를 붙이면 그 값에 따라 세그먼트에 배정되는 것을 콘솔에서 확인합니다.
4. 리전을 하나 더 쓰는 환경에서, 같은 세그먼트에 속한 연결이 리전을 넘어 통신하는 것을 확인합니다.
5. Site-to-Site VPN으로 온프레미스를 core network에 연결하고 BGP 경로를 확인합니다.
6. policy version을 만들고 change set을 검토·실행해 통신할 수 있는 범위를 바꿉니다.
7. 같은 요구사항을 Transit Gateway로 만들 때와 비교해 무엇이 달라지는지 설명합니다.

## 1-1-c. 시나리오 { #scenario }

여러분은 한 고객의 네트워크 담당자입니다. 고객은 다음 네 가지를 요구합니다.

1. 운영 환경과 개발 환경은 서로 통신하면 안 됩니다.
2. 공유 서비스(로그, 인증, 모니터링)는 운영과 개발 양쪽에서 쓸 수 있어야 합니다.
3. 온프레미스는 운영과 공유 서비스에는 닿아야 하지만, 개발에는 닿으면 안 됩니다.
4. 미국(오레곤)에 운영 환경을 하나 더 엽니다. 서울의 운영 환경과 통신해야 합니다.

### 세그먼트 설계

네 가지 요구사항을 세그먼트 4개로 옮기면 다음과 같습니다.

| 세그먼트 | 담는 연결 | 기본 동작 |
|---|---|---|
| `prod` | 서울 prod VPC, 오레곤 prod VPC | 같은 세그먼트끼리만 통신합니다 |
| `dev` | 서울 dev VPC, 오레곤 dev VPC | 같은 세그먼트끼리만 통신합니다. 오레곤 dev VPC는 추가 과제 [3-1](extra-a.md)에서 붙입니다 |
| `shared` | 서울 shared VPC | `prod`, `dev`, `onprem`에 share합니다 |
| `onprem` | Site-to-Site VPN attachment | 처음에는 `shared` 와만 통신합니다. `prod` 는 [2-4](lab3.md)에서 엽니다 |

그림 1에서 눈여겨볼 곳은 세 가지입니다.

- `prod`와 `dev`가 통신하지 못하는 것은 **아무 설정도 하지 않았기 때문**입니다. 막으려고 규칙을 넣은 것이 아닙니다. 이 기본 동작은 [2-2](lab1.md)에서 ping으로 먼저 확인합니다.
- `shared`가 `prod`·`dev`·`onprem`에 share하면, 세 세그먼트는 `shared`에 닿지만 서로는 여전히 닿지 않습니다. 이 비대칭이 공유 서비스 패턴의 핵심입니다.
- `onprem`은 `shared`와만 통신하는 상태로 시작합니다. 운영 환경에는 닿지 않습니다. [2-4](lab3.md)에서 정책에 `share` 한 줄을 넣어 온프레미스와 운영 환경을 엽니다.

`prod` 세그먼트에는 서울과 오레곤의 VPC 연결이 함께 들어갑니다. `dev` 세그먼트도 추가 과제 [3-1](extra-a.md)에서 오레곤 dev VPC를 붙이면 두 리전에 걸칩니다. 같은 세그먼트에 있으면 리전이 달라도 통신합니다. 세그먼트를 리전마다 따로 만들거나 리전 사이를 잇는 설정을 넣을 일은 없습니다.

### 주소 설계 { #addressing }

참가자마다 계정이 다르므로 주소는 모든 참가자가 똑같이 씁니다. 참가자 번호 같은 값은 없습니다.

| 구분 | 리전 | 대역 | 테스트 호스트 |
|---|---|---|---|
| 온프레미스 모사 LAN | 서울 | `172.16.1.0/24` | `172.16.1.10`(온프레미스 VM) |
| prod VPC | 서울 | `10.10.1.0/24` | `10.10.1.10` |
| dev VPC | 서울 | `10.20.1.0/24` | `10.20.1.10` |
| shared VPC | 서울 | `10.30.1.0/24` | `10.30.1.10` |
| prod VPC | 오레곤 | `10.11.1.0/24` | `10.11.1.10` |
| dev VPC | 오레곤 | `10.21.1.0/24` | `10.21.1.10` |

워크로드 VPC(prod, dev, shared)의 EC2는 모두 프라이빗 서브넷에 있습니다. 인터넷에서 직접 접속할 수 없고, 접속은 **EC2 Instance Connect Endpoint**로 합니다.

서울 EC2에는 `tcpdump` 같은 진단 도구가 들어 있습니다. 오레곤 EC2는 ping과 HTTP 응답을 받아 주는 **대상 전용**이라 진단 도구를 설치하지 않습니다. 패킷을 들여다볼 일이 있으면 서울 쪽 EC2에서 합니다.

온프레미스 모사 VPC는 Cloud WAN에 VPC 연결로 붙이지 않습니다. 오직 Site-to-Site VPN으로만 연결합니다. 그래야 실제 온프레미스와 같은 경로로 동작하고, BGP로 경로를 주고받는 것도 확인할 수 있습니다.

ASN은 다음과 같이 씁니다. core network edge의 ASN은 만든 뒤에 바꿀 수 없으므로 템플릿에서 리전별로 미리 정해 둡니다.

| 구분 | ASN |
|---|---|
| core network `asn-ranges` | `64512-64520` |
| 서울 core network edge | `64512` |
| 오레곤 core network edge | `64513` |
| 온프레미스 라우터, 그리고 그것을 등록한 customer gateway | `65000` |

**라우터와 customer gateway는 같은 것이 아닙니다.** 라우터는 온프레미스에 있는 실제 장비(이 워크숍에서는 그 역할을 하는 EC2)이고, **customer gateway** 는 그 장비의 공인 IP와 ASN을 AWS에 등록해 둔 리소스입니다. AWS는 customer gateway를 보고 어디로 터널을 걸지 압니다. 표에 한 줄로 적은 것은 **둘이 같은 장비를 가리키기 때문에 ASN도 같은 값** 이어서입니다. 장비와 리소스가 같은 것이라는 뜻은 아닙니다.

### 누가 무엇을 만드나요

학습 목표에 직접 닿는 것만 참가자가 직접 만듭니다. 나머지는 CloudFormation 스택 2개가 미리 만듭니다.

스택이 만드는 것은 다음과 같습니다. 강의 전에 배포를 시작합니다([2-1](lab0.md)).

| 스택 | 무엇을 |
|---|---|
| 서울 스택 | global network, core network(초기 정책과 세그먼트 4개, core network edge 2개), prod·dev·shared VPC와 EC2, 온프레미스 모사 VPC와 VPN 라우터·VM, 서울 VPC 연결 3개, customer gateway |
| 오레곤 스택 | prod VPC와 EC2, dev VPC와 EC2 |

오레곤 스택은 VPC와 EC2만 만들고 **연결(attachment)은 만들지 않습니다**. 연결을 붙이는 것과 VPC 라우트를 넣는 것은 참가자가 직접 합니다.

| 참가자가 콘솔에서 직접 만드는 것 | 어디에서 |
|---|---|
| 오레곤 **prod** VPC 연결과 그 VPC의 라우트 | 본편 [2-2](lab1.md) |
| Site-to-Site VPN 연결, Cloud WAN VPN attachment, 온프레미스 라우터 터널 설정 | 본편 [2-3](lab2.md) |
| policy version 만들기, change set 검토와 실행 | 본편 [2-4](lab3.md) |
| 오레곤 **dev** VPC 연결과 그 VPC의 라우트 | 추가 과제 [3-1](extra-a.md) |

오레곤 dev VPC 연결만 추가 과제입니다. 본편 실습([2-2](lab1.md)~[2-4](lab3.md))에서는 만들지 않습니다. 추가 과제 [3-1](extra-a.md)에서 이 연결을 붙이면 `dev` 세그먼트가 두 리전에 걸치고, 그 상태에서 연결 격리 옵션의 효과를 서울 dev와 오레곤 dev 사이의 통신으로 확인합니다.

core network policy를 어떻게 읽는지는 [4-1. core network policy 읽는 법](concepts.md)에 정리했습니다. Transit Gateway로 같은 구성을 만들 때와의 비교는 [3-2. Transit Gateway와 비교](extra-b.md)에 있습니다.

## 1-1-d. 진행 순서 { #schedule }

| 시간 | 구분 | 내용 |
|---|---|---|
| -0:10–0:00 | [2-1](lab0.md) | 로그인, 스택 2개 배포 시작(이론 강의 전에 합니다) |
| 0:00–1:00 | 이론 | Cloud WAN 강의. 강의 중에 core network가 완성됩니다 |
| 1:00–1:22 | [2-2](lab1.md) | core network 둘러보기, 세그먼트 격리 확인, 오레곤 연결 추가 |
| 1:22–1:42 | [2-3](lab2.md) | 온프레미스 VPN 연결과 BGP 경로 확인 |
| 1:42–1:57 | [2-4](lab3.md) | 정책 한 줄로 온프레미스 열기 |
| 1:57–2:00 | [3-4](extra-d.md) | 참가자가 만든 연결 삭제, 스택 삭제 시작 |

!!! warning "스택 배포는 이론 강의 전에 시작합니다"
    core network를 처음 만들 때는 **최대 30분**이 걸립니다. 그 동안에는 연결을 만들 수도, 정책을 고칠 수도 없습니다. 그래서 스택 배포를 이론 강의 **전에** 시작해, 강의 1시간 동안 끝나 있게 합니다. 강의가 끝나면 바로 실습을 시작할 수 있습니다.

[3-4. 리소스 정리](extra-d.md)는 시간이 모자라도 꼭 마지막에 합니다. 참가자가 만든 연결을 먼저 지워야 스택이 지워집니다.

### 추가 과제의 예상 소요 시간 { #extra-time }

추가 과제 [3-1](extra-a.md), [3-2](extra-b.md), [3-3](extra-c.md)은 시간이 남거나 워크숍 뒤에 혼자 더 해 볼 분을 위한 것입니다. 본편 1시간 배분에는 들어 있지 않습니다.

| 과제 | 예상 시간 | 무엇이 시간을 쓰나 |
|---|---|---|
| [3-1. 연결 승인과 격리 옵션](extra-a.md) | **25~30분** | 넷 중 가장 깁니다. 오레곤 dev 연결을 하나 더 만들고(`Available` 까지 4분쯤), 정책 버전을 세 번 만들어 실행합니다(한 번에 2분쯤). EC2 접속과 ping도 들어갑니다 |
| [3-2. Transit Gateway와 비교](extra-b.md) | **5~10분** | **읽기만 합니다.** 콘솔을 만지지 않으므로 기다릴 일이 없습니다 |
| [3-3. 경로 테이블과 지표 보기](extra-c.md) | **10분 안팎** | 세그먼트를 바꿔 가며 경로를 조회합니다. 만드는 것이 없어 기다림이 없습니다 |
| [3-4. 리소스 정리](extra-d.md) | **20분 남짓** | 선택이 아니라 **반드시** 합니다. 대부분이 마지막 서울 스택 하나(15분쯤)입니다 |

셋을 다 하면 **40~50분**, [3-4](extra-d.md)까지 더하면 **1시간쯤**입니다.

!!! tip "시간이 모자라면 3-2부터 보세요"
    [3-2](extra-b.md)는 읽기만 하면 되고 [3-3](extra-c.md)은 조회만 합니다. 만드는 것이 없어서 언제 멈춰도 뒷정리가 늘지 않습니다. 반대로 [3-1](extra-a.md)은 연결을 하나 더 만들고 정책을 세 번 고치므로, 시작했다면 [3-1-g](extra-a.md#a-g)의 되돌리기까지 끝내는 편이 좋습니다.

!!! info "표의 배분은 목표치입니다"
    오래 걸리는 것은 **core network 생성(15분쯤)** 과 **서울 스택 삭제(15분쯤)** 둘뿐이고, 둘 다 기다리는 동안 다른 일을 할 수 있게 배치했습니다. 나머지 동작은 각각 몇 분입니다. 소요 시간은 해당 소절에 적어 두었습니다.

    진행 속도에 따라 묶음별 시간은 조금씩 달라집니다.
